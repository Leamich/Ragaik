# Правила ведения проекта

## 1. Среда разработки

1.1 Используйте **WSL Ubuntu** или **Mac** для разработки.

1.2 Для управления зависимостями применяйте **uv**:
- `uv add` — добавление зависимостей
- `uv sync` — синхронизация зависимостей
- `uv venv` — создание виртуального окружения

1.3 Если используете **VS Code** или **Cursor**, установите следующие расширения:
- `Black Formatter`
- `Mypy Type Checker`
- `Pylance`
- `Pylint`

Если используете другую IDE, применяйте аналогичные инструменты.

---

## 2. Общие правила написания кода

2.1 Мы разрабатываем **микросервисы**. Для каждого микросервиса создавайте отдельное виртуальное окружение.

2.2 Используйте **типизацию** повсеместно.

2.3 Пишите **docstrings** для всех модулей и функций, кроме `__init__` файлов. Докстринги должны быть подробными.

2.4 Следуйте рекомендациям линтеров и статических анализаторов — они правы.

2.5 Применяйте **type alias** для улучшения читаемости кода.

2.6 Не коммитьте код, который вы не понимаете.

2.7 Пишите **тесты**.

2.8 Не изобретайте существующие типы заново. Например, не реализуйте повторно `Document` из `langchain`.

2.9 Для реализации интерфейсов используйте `ABC` (Abstract Base Classes).

2.10 Используйте понятный и нейтральный **нейминг** без шуток и мемов.

---

## 3. Организация кода

3.1 Весь **backend** хранится в модуле `backend`.

3.2 Каждый **submodule** backend'а — отдельный сервис (например, `rag`).

3.3 Текущие сервисы: `rag_service`, `gpu_heavy_service`. Список будет расширяться.

3.4 Каждый сервис должен содержать $\le 1$ графа из **LangGraph**. Он может содержать дополнительные точки входа с небольшим количеством функций (например, сохранение документа в `rag_service`, но не его предобработку).

3.5 Сервис должен состоять из:
- `main.py`
- `README.md`
- конфигов
- модулей `tests` и `src`

3.6 Структура `src` обычно включает модули:
- `application` — API и связанные элементы
- `domain` — доменная логика, работа с конфигами, связывание инфраструктурных компонентов
- `infrastructure` — инфраструктурные компоненты
- `schema` — type alias'ы и состояния графов

3.6.1 **infrastructure** — инфраструктурные модули: взаимодействие с внешними сервисами, хранилищами и т.д.

3.6.2 **domain** — реализация логики приложения, настройка параметров (например, выбор LLM модели из конфига).

3.6.3 **application** — точки входа (API) и их обработка.

3.6.4 **schema** — типы данных, схемы, состояния графов.

3.7 В `infrastructure` должны быть:
- `adapters` — абстрактные классы
- предметные модули — реализации абстрактных классов для конкретных задач (например, `document_stores`, `llms` и др.)

3.8 Абстрактные классы описывают, как обернуть внешние компоненты (например, клиент БД или эмбеддер) для использования в проекте.
